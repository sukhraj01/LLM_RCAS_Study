## Key Decisions

- **Read the installed `optimum` source directly instead of trusting the engineer's stated root cause at face value.** The engineer's hypothesis was "torch.onnx export needs the full model resident in GPU memory and simultaneously trace the graph." Reading `optimum/onnxruntime/modeling_decoder.py`'s `_export()` and `optimum/exporters/onnx/__main__.py`'s `main_export()` (installed version, `optimum[onnxruntime]>=1.19.0` unpinned — no `requirements.lock.txt` committed yet, so this is the best available proxy for what's on Kaggle) showed `main_export`'s `device` parameter already defaults to `"cpu"`, and the old code's `ORTModelForCausalLM.from_pretrained(model_id, export=True, provider="CUDAExecutionProvider", ...)` call never overrode it — so in this installed version, the *trace itself* wasn't necessarily happening on GPU by default. Found a second, more concrete and directly verifiable cause instead: `main_export`'s `dtype` parameter defaults to `"fp32"` whenever not explicitly set (confirmed at `optimum/exporters/onnx/__main__.py:183-184`), and the old code never set it. A fp32 export of a 7B model is ~28GB — double the fp16 baseline's ~14GB that fits fine — so loading that graph onto a 16GB GPU via `CUDAExecutionProvider` (which the old code did do, via the `provider="CUDAExecutionProvider"` kwarg forwarded into the post-export `_from_pretrained` call) would OOM on its own, regardless of where tracing happened. Reported both mechanisms rather than silently substituting my finding for the engineer's without explanation, since the engineer explicitly asked to review the diff/logic before spending more Kaggle GPU hours.
- **Did not use `ORTModelForCausalLM.from_pretrained(model_id, export=True, ...)` at all for the fix**, since tracing through its source showed no way to pass `dtype="fp16"` through that path in this optimum version — `_export()`'s `**kwargs` are only forwarded to the post-export `_from_pretrained()` call (session/provider options), never into the `main_export()` call itself. Called `optimum.exporters.onnx.main_export()` directly instead, which is the documented, public, stable entry point for controlling `device`/`dtype` at export time (same function `optimum-cli export onnx` uses), then loaded the resulting `onnx_dir` via `ORTModelForCausalLM.from_pretrained()` for the GPU inference/benchmarking step — cleanly separating export (CPU, fp16) from benchmarked inference (GPU, `CUDAExecutionProvider`) exactly as the engineer asked.
- **Implemented the "first run only, reuses onnx_dir" caching behavior for real** rather than treating the engineer's "keep it intact" instruction as a no-op. The pre-existing code's docstring/print statement described this caching behavior, but the actual call (`ORTModelForCausalLM.from_pretrained(model_id, export=True, ...)` unconditionally, every run) never checked whether `onnx_dir` already had a prior export — it silently re-exported and overwrote every time. Added a real `os.path.isdir(onnx_dir) and any(f.endswith(".onnx") for f in os.listdir(onnx_dir))` guard so the claimed behavior is now true, not just documented.
- **Added `maybe_save_preprocessors(model_id, onnx_dir)` after export** (mirrors what `optimum`'s own `_export()` classmethod does internally) so `onnx_dir` stays a fully self-contained, independently reloadable export directory — not strictly required by this script (the tokenizer is loaded separately from `model_id`, not from `onnx_dir`), but keeps the exported directory consistent with what optimum itself produces and avoids a latent gap if the directory is ever reloaded standalone.
- **Did not attempt to "fix" `experiments/llama/05_onnx.py` the same way and call it done.** Applied the identical CPU/fp16 export pattern (it's the correct fix mechanically), but added an explicit, loud comment and a dedicated "Open Risk" section in both `EXPERIMENT_MATRIX.md` and `PROJECT_STATE.md` stating that Llama-2-13B's fp16 weights alone (~26GB) exceed 16GB VRAM before any export overhead — meaning even a correctly CPU-exported fp16 graph likely can't be loaded back via `CUDAExecutionProvider` on this hardware — and that Kaggle's CPU RAM headroom for holding a ~26GB model during tracing has not been checked. Per the engineer's explicit instruction 5, framed this as an open risk requiring a decision before scheduling, not something the same fix trivially resolves.
- **Verified only what's possible without a GPU, and said so plainly rather than implying more confidence than warranted:** `py_compile` on both scripts, a full module-level import against the real installed `optimum`/`torch`/`transformers` stack (catches import errors and API-signature mismatches, e.g. would have caught it if `main_export` didn't actually accept `device`/`dtype`), and `inspect.signature(main_export)` confirming `device`, `dtype`, `output`, `model_name_or_path`, `task`, and `token` are all real parameters of the installed version.

## Key Decisions

- **Did not accept the engineer's "safe" claim about cache deletion at face value — verified it by reading transformers' actual loading code.** The engineer's own instructions called this "safe" but flagged it as their own reasoning, not a verified fact. Read `transformers/modeling_utils.py`'s `load_state_dict()` and confirmed safetensors shards are loaded inside a `with safe_open(...) as f: ... f.get_tensor(k)` block — `get_tensor()` copies each tensor into a fresh torch-owned buffer, and the `with` block closes the underlying file/mmap before `from_pretrained()` returns. This meant no lingering file handle from the loading process would keep deleted disk blocks alive at the OS level (relevant because on POSIX systems, unlinking a file while a process still holds it open via mmap does *not* actually free the underlying disk blocks until every reference is closed — had `get_tensor()` returned a persistent mmap-backed view instead of a copy, deleting the cache could have silently failed to free space, or worse, corrupted the model once accessed after deletion). Reported this verification finding explicitly rather than silently trusting the engineer's premise.
- **Went beyond "verify offline as much as possible" by actually running the fix, not just checking it compiles.** The enginen's instruction acknowledged a GPU wasn't available and asked for offline verification, but `onnx_export_from_model`, `AutoModelForCausalLM.from_pretrained`, and `huggingface_hub.scan_cache_dir` don't require a GPU — CPU-only export was always the point of this fix. Confirmed network access was available in this sandboxed environment and ran the *entire* pipeline (load fp16 → free cache → confirm the model still works post-deletion → export → reload → generate) against `hf-internal-testing/tiny-random-MistralForCausalLM`, a real, tiny, same-architecture-family stand-in model, rather than settling for `py_compile`/import-only verification like the previous two ONNX fix attempts. This is a materially stronger verification standard than what was possible for the VRAM and first disk fixes, and worth flagging as a distinction rather than describing all three fixes as "verified offline" uniformly.
- **Ran a second, negative-control test (tiny GPT2) and reported the failure it produced, rather than only reporting the passing test.** The GPT2 test failed with an ONNX Runtime `LayerNormalization` fp16/fp32 dtype-mismatch error during the internal graph-validation step (`fix_dynamic_axes` → `InferenceSession` construction) — a real failure, not a fluke. Investigated whether this was a flaw in the new export logic (it wasn't — the identical code path succeeded on the Mistral-architecture test) or an architecture-specific ONNX-export quirk (it was — Mistral uses RMSNorm and has no `LayerNormalization` op in its graph at all, so this specific failure mode cannot occur for the real experiment). Reported both results plainly, including the caveat that this was confirmed on a tiny stand-in rather than the real 7B model, instead of quietly omitting the GPT2 failure because it didn't affect the final recommendation.
- **Did not need to invoke the engineer's fallback ("defer as an open risk if this requires a fragile reimplementation").** `onnx_export_from_model()` turned out to be a first-class, documented, stable part of optimum's public API — its own docstring shows the exact load-then-export pattern needed, and it internally handles everything `main_export()` does (OnnxConfig construction, task inference, opset selection, config/generation_config/preprocessor saving) without requiring any reimplementation. This made the fix legitimate rather than shaky, so proceeded with implementing and verifying it rather than escalating to the deferral option — but kept the engineer's stated bar in mind throughout: if `onnx_export_from_model` had required custom OnnxConfig construction or other Mistral-specific reimplementation, the right call would have been to stop and report that plainly instead.
- **Refined the Llama-2-13B disk-risk framing rather than leaving it stale.** The existing Llama "Open Risk" entry (from the previous session) was written assuming the `/opt/bin`-redirect-based fix; now that the real fix is "never hold cache and output on disk simultaneously" rather than "redirect to a bigger mount," recomputed what that means for Llama specifically: even with the improved fix, Llama's *peak* single-phase disk usage is still ~26GB (13B fp16 weights), which alone exceeds the ~20GB quota regardless of overlap — so the fix helps Mistral fully but does not help Llama at all. Updated both `EXPERIMENT_MATRIX.md` and `PROJECT_STATE.md` to state this precisely rather than leaving an outdated "CPU export may be the only option" framing that no longer matches the current fix's actual mechanism.
